# Dola 上传出口分离与分时流量统计分析

日期：2026-10-01。范围：当前 Web 后台、Dola Python Provider、共享代理服务与部署配置。此次为代码分析和本地定向测试，没有修改代理绑定，没有调用真实 Dola/付费代理，没有实施业务代码改造。

## 结论

参考图上传已经支持独立出口：Dola 提交使用通用/链式代理时，ImageX Apply、二进制 POST 上传、Commit 可以使用直连或独立魔法代理。Web 后台的「Dola API → 代理管理」已经分别呈现 Dola API 与 Dola 参考图上传两个配置卡片。

当前仍不能保证所有大流量避开付费代理：普通外部 URL 参考图下载沿用提交代理；Camoufox 页面资源沿用账号代理；结果下载使用服务器公共出站策略，未显式固定为直连。现有后台没有按代理端口和时间范围统计真实流量的完整能力。

独立上传的含义是独立代理配置和客户端，并不意味着三个请求一定使用同一 TCP 连接或出口 IP：Apply/Commit 与文件上传可能访问不同主机，旋转代理也可能按新连接换 IP。项目签名代码没有加入客户端源 IP，但上游是否接受跨出口凭据仍需真实样本验证，不能由本地 mock 推定。

HTTPX 官方说明支持按客户端配置代理，且 `trust_env=False` 禁止环境变量代理自动接管：

- [HTTPX 代理](https://www.python-httpx.org/advanced/proxies/)
- [HTTPX 环境变量](https://www.python-httpx.org/environment_variables/)

## 流量仍可能发生在哪里

1. **外部参考图下载**：`upload_reference()` 把提交代理传给 `_fetch_source_bytes()`。普通 HTTPS 图片会通过该代理下载，然后才经独立出口上传。单张图片即使上传直连，下载仍可能消耗与原图大小接近的付费代理流量。
2. **站内签名素材读取**：`/api/reference-assets/...` 且具有 provider-read 签名参数时，读取走直连，可通过 `DOLA_REFERENCE_ASSET_ORIGIN` 改为内部地址。这部分已经避免付费代理。Data URL 不需要额外下载；已有 URI 跳过重新上传。
3. **浏览器资源**：Python Provider 创建使用账号代理的 Camoufox 并加载 Dola 页面，目前未发现公共脚本、图片、字体与媒体的独立出口路由。页面启动流量不能归为少量生成请求。Dola Studio 桌面已有公共资源直连选项，Web Provider 尚未采用同等逻辑。
4. **结果媒体下载**：外部 API 视频 content 与公共媒体下载调用 `fetchSafeOutbound()`，没有注入 Dola 提交代理，但也没有设置 `directOnly`。该 helper 会使用服务器全局代理。因此不能简单宣称成片一定直连；是否消耗同一付费代理取决于公共出站配置。
5. **无水印地址解析**：相关 VOD JSON 请求使用 Dola 提交代理。它属于控制请求，与成片二进制下载需要分别统计。
6. **其他参考素材**：当前上传协议是图片 ImageX，首帧/尾帧也复用图片路径。不能据此宣称已支持参考视频、音频或任意文件上传；新增类型必须核对真实协议。
7. **多图客户端复用**：每张图内的 Apply/上传/Commit 复用客户端，但 `resolve_references()` 每张图重新创建客户端，尚未实现整个多图任务共用上传客户端。
8. **部署差异**：主 Compose、offline 与 offline-external-db 已注入上传 17894 配置；local、external-db、lowmem、baota Compose 尚未注入对应的 Dola 上传 PORT/URL。直连不依赖该监听端口，魔法上传需补齐部署环境。

建议保留登录、签名、prepare_upload、生成提交、任务查询和真实安全挑战的账号出口；参考素材下载、图片二进制上传、结果媒体及可明确识别的公共资源单独走低成本出口。独立出口失败时展示具体阶段，禁止静默改走付费代理。静态资源分流应限定公开资源与域名，不对所有 GET 请求粗暴直连。

通用代理配置本身不能保证每次 HTTP 请求出口 IP 都不同；实际取决于供应商会话、连接复用及轮换机制。此次未探测真实出口，也没有改变既有轮换策略。

## 现有统计为何不够

- `DolaRequestLog.requestBytes/responseBytes` 主要记录 Web 与本地 Provider 的请求、JSON 回复，部分媒体接口记录 Content-Length；不是统一的真实代理传输计量。
- 同一任务的轮询会更新原日志的 responseBytes，并非累加所有请求。
- 上传文件、浏览器资源、失败时已发送字节、重试流量和部分接收流量没有完整入账。
- 现有统计页展示账号数、成功数、失败数；没有时间范围和端口流量。
- 日志只保留最近 10,000 条，不适合充当长期流量账本；没有采集的数据不能补算为历史真实流量。

## 后台分时流量统计方案

建议在现有「统计报表」增加流量区，并在「代理管理」展示所选出口在相同时间范围内的摘要。

筛选条件：今天、昨天、近 7 天、近 30 天、自定义开始/结束时间；提交、素材拉取、上传、查询、公共资源、结果下载；代理类型、逻辑节点、本地入口端口、上游代理主机与端口。界面使用北京时间，存储使用 UTC，查询区间采用 `[开始, 结束)`。

展示：发送字节、接收字节、总流量、连接/请求数、失败次数、按小时/天趋势、每端口排名、直连/魔法/通用/链式占比。失败与人工重试产生的实际传输也必须计入。采集开始前或采集中断的区间应明确标为缺失。

端口不能单独作为身份：两个代理主机都可能使用 8080；17893 是本地入口，不是付费供应商的远端端口。计量身份需要服务、角色、稳定节点 ID、本地入口、上游主机/端口及生效路由版本；显示脱敏地址，禁止保存 URL 中的账号密码。

建议分两个口径实现：

1. **业务传输计量**：在 Python HTTPX 与 Web 媒体流读取/发送处按实际消费的字节记录任务、阶段、出口及时间。成功、失败、中断、重试均记账；不以 Content-Length 或一次任务结果代替累计传输。
2. **代理转发计量**：统一覆盖魔法、链式和直接连接通用代理的路径，读取成熟转发层的持久计数或增加使用成熟组件的计量网关，并覆盖 Camoufox 资源。不能仅依赖打开后台页面才进行采集。网关须保持现有账号、连接和代理轮换语义。

Mihomo `/traffic` 提供全局实时流量，`/connections` 提供活跃连接上传/下载累计值与链路。源码 metadata 包含 `inboundName/inboundPort`，可用于入口拆分，但必须核对部署内核版本。它们适合实时观察；连接关闭会移出活跃集合，快照间完成的短连接会被遗漏，不能仅靠快照差分宣称完整历史账本。通用代理路径当前直接返回代理 URL，绕过 Mihomo，还需独立采集。

- [Mihomo API](https://wiki.metacubex.one/api/)
- [Mihomo 连接元数据](https://github.com/MetaCubeX/mihomo/blob/Meta/constant/metadata.go)
- [Mihomo tracker 计数与关闭](https://github.com/MetaCubeX/mihomo/blob/Meta/tunnel/statistic/tracker.go)

链式请求经过跳板和落地是同一业务传输，业务总量只计算一次；各供应商的计费消耗可分别展示，不得把两跳相加当作上传了两份文件。平台字节口径与供应商账单可能因协议开销和计费规则不同，若需准确费用/余额必须另外接入供应商官方账单能力。

流量事件或增量计数应独立持久化，采用幂等事件身份/游标，支持进程重启及并发；聚合按时间窗和出口定向查询，使用 bigint 字节字段。增加 repository 时同步 `docs/backend-database.md`，保留现有文件 Provider 的服务端回退。长连接跨时间边界应按持续传输增量归入对应时间桶，不能把全部字节记到开始或结束时间。

## 建议实施顺序与验收

1. 沿用现有上传绑定；补齐外部素材下载、结果下载、公开浏览器资源分流、多图客户端复用及部署变量。
2. 补充稳定且脱敏的路由身份和分阶段实际字节计量；再覆盖所有代理转发路径的持续采集与持久化。
3. 提供管理员统计接口、时间范围、端口/节点排行与趋势；API 与所有可见汇总使用同一筛选范围。
4. 本地 TCP fixture 分别验证直连、魔法、通用、链式，确保二进制未流经付费提交出口；覆盖首尾帧、多图、错误、中断、重试、短连接、并发、计数重置、进程恢复及跨日统计。
5. 按项目规范运行类型检查、相关/全量质量门禁、生产构建并重启，回归后台桌面与 390px/430px、浅深主题、筛选和刷新持久化。
6. 若后续授权真实上游验收，使用真实账号验证 prepare_upload 经账号出口、ImageX 经独立出口仍可生成，并读取真实代理转发字节。供应商账单对账单独报告。
