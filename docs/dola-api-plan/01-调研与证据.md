## 3. 原五个参考项目与新增项目结论

### 3.1 dou3bao3-main：可参考链路，不能原样部署

来源：[jiyongdian/dou3bao3](https://github.com/jiyongdian/dou3bao3)。本地 `LICENSE` 为 MIT；若移植许可范围内代码，保留署名与许可证。以本地源码为分析依据，未执行其安装、系统调优、自更新或远程脚本。

`SOURCE`：FastAPI + Playwright；`app/main.py` 提供 `/v1/videos/generations`、状态查询与管理路由；`automation.py` 负责页面会话、上传、`/chat/completion`；`query.py` 查询 `/im/chain/single` 和 `/im/conversation/info`。

关键问题及处理：

1. `DolaFetchAutomation._run_once()` 每任务 `browser.new_context()`，没有加载导入账号 Cookie 或 storageState。结束后读取的是此次新 context 的 Cookie。这不是用户需要的已授权多账号池。
2. `config.py::normalize_video_model()` 无视入参，总返回 `seedance_v2.0`；`SUBMIT_SCRIPT` 的 `ability_param.model` 也写死同值。离线输入 `seedance_v2.5` 仍得到 2.0 字符串。该字符串是否在当前 Dola 映射至 2.5 需抓包，不能仅凭名称判断实际模型。
3. `resolution` 在调用链传入，但提交能力参数只明确使用 ratio/model/duration。不能声称清晰度参数生效。
4. `mark_success()` 表示浏览器提交流程完成，不表示成片成功。查询结果中的 code=0/1/2 还需要重新标准化；本项目成功必须有真实持久媒体。
5. `worker.py` 遇异常把任务重新置为 pending，随后再次运行提交。这会把“已创建但响应丢失”变成重复生成。
6. `query.py` 在没有准确会话 ID 时读取 recent conversation；共用账号并发会串单。接入时禁止这个兜底，改为稳定消息/会话关联和待核对状态。
7. 查询成功后删除 Cookie/会话关联，仅保留下载 URL；临时链接过期后的恢复能力不足。
8. `/v1/chat/completions` 实际创建视频；embeddings 返回固定零向量，moderations 返回固定未标记。三者都不能作为对应真实能力暴露。
9. 配置存在公开固定默认 Token；Cookie、原始 SSE 可写入任务结果。必须改为独立随机服务凭据与加密账号存储、白名单脱敏日志。
10. 有历史 UA/版本/身份值、浏览器环境改写及固定等待。新实现使用真实会话及可验证协议，不移植这些伪装、拍脑袋重试或等待。

结论：可以借鉴上传和异步结果解析结构；不具备“换域名即可接入”的条件。启动成功也不能证明账号反代可用。本轮没有使用真实账户运行此服务。

### 3.2 dola-30s-unlocker-main：前端选项修改不等于上游授权

来源：[microshark2024/dola-30s-unlocker](https://github.com/microshark2024/dola-30s-unlocker)。本地未找到独立 LICENSE。

`SOURCE`：`hook.js` 改写 fetch/XHR；用内置 `DOLA_SKILL_PACK_DATA` 替换 `skill/pack` 类响应；修改 Action Bar 配置、递归扩展 `supported_durations`；观察 `im/chain/single` 的响应以提取结果。

重要区别：它主要让网页选项可选，再让网页组装请求；不是一个已经独立实现 Dola 视频 API 的后端。内置模型字符串包括 `seedance_v2.0_std`、`seedance_v2.0`、`seedance_v2.0_mini`；当前页面名与 wire ID 关系需要实测。不能向本项目复制整份静态技能包作为官方模型目录，也不能假定补 `duration=30` 就足够。

接入方法：用同一模型的真实 10 秒请求作基线，比较 15/30 秒的功能字段；将验证所得最小差异封装在 Dola 参数编译器，不修改最终用户的 Dola 页面或要求安装扩展。README 提到直提无水印链接已失效；当前是否所有视频都有同一种水印仍须真实素材验证。

### 3.3 dola-watermark-remover-main：本地可运行，需工程化与质量验证

来源：[microshark2024/dola-watermark-remover](https://github.com/microshark2024/dola-watermark-remover)。本地未找到独立 LICENSE；模板图同样需要确认可复用来源，必要时用自有测试视频重新标定。

`SOURCE`：`remove_dola_watermark.py` 读取 `assets/tpl_precise.png`、`mask_precise.png`；灰度/梯度模板匹配 → 分段轨迹与线性拟合 → 动效外推 → 复合蒙版 → OpenCV Telea inpaint → H.264 输出 → 音轨合成。不是解密，也不是返回另一个所谓无水印原文件。

`OFFLINE`：用本地模板置于合成背景，生成 8 帧、24fps 的 1280×720 和 640×360 两个视频；两次 `process_video()` 均返回 true，并生成输出文件。只证明依赖、模板、解码和处理流程能运行，不证明真实 Dola 视频修复质量，也没有覆盖音频。

需要修正的工程问题：

- `frames.append(frame)` 缓存整片。30 秒、24fps、1280×720 的 BGR 像素约 1.85 GiB；1920×1080 约 4.17 GiB，尚未含副本和匹配矩阵。采用两遍流式处理，第一遍仅保存轨迹，第二遍重新解码修复。
- 参考实现按宽度相对 1280 缩放模板；竖屏、不同水印版本及动态内容可能误检，要单独标定。
- `remux_audio()` 实际使用 `-c:a aac`，不是 README 所称的所有音轨无损复制；异常时保留静音视频且主函数仍可返回成功。新实现不能把丢音轨当成功。
- 同 PID 固定临时文件名可能冲突，异常清理不完整；要用 task 独立临时目录、finally 清理、原子落盘。
- 即使没有可信检测轨迹也会输出成功文案。需要明确 `no_watermark_detected` / `needs_review`，不能凭函数返回值宣称已经去净。
- 算法有损修复可能抹掉人物、文字和纹理。记录算法版本、检测覆盖及原片关联，允许对比和仅重试后处理。

## 5. 阶段 A：真实协议验证运行手册

### 5.1 建立证据目录

实施后增加 `docs/dola-api-plan/evidence/live/`，仅保存脱敏样本与结果摘要。原始 HAR、Cookie、签名媒体地址不能进入 Git、普通请求日志或发布包。原始捕获如确需临时保存，放权限受限、被忽略的本机目录，脱敏后清理；不要把整个浏览器 Profile 拷入项目。

每个样本记录：caseId、模型 UI 名、当前 wire model ID、transport、入口、比例、时长、引用数量/角色、功能字段、HTTP/业务状态、任务阶段、匿名账号标签、逻辑请求 ID、生成结果、文件规格、证据文件哈希。会话、媒体、设备 ID 在共享样本中采用稳定占位映射，以便证明关联而不暴露原值。

### 5.2 捕获顺序

1. 在已登录页面查看 DevTools Network，保留日志并按 chat/completion、im/chain、resource、skill/action_bar 和账户额度相关请求过滤。不安装未审核插件，不修改网站源代码。
2. 先只读刷新能力配置与账号信息，确定完整 origin/path/method/content-type 和返回状态；记录响应真实字段。没有独立余额端点时明确记录“无可读精确额度”，不要猜 `/quota`。
3. 真实提交简单 2.5 / 5 秒文生视频；保存请求功能结构、SSE 事件与 conversation/message/task 关联；等待终态并下载一次验证。不把 SSE 断开视作生成失败。
4. 使用同一账号、同一模型、同一比例完成 10 秒基线。记录相对 5 秒的差异，以及 2.5 与其他模型的映射来源。
5. 在受控实验中仅修改已识别的时长功能字段，分别验证 15/30 秒；如果还有模型档位或模式差异，逐项对照真实功能配置。一次只变一个变量。返回权限、额度、限制错误就记录事实，不能靠伪造账号/重放旧签名继续尝试。
6. 使用自有无隐私测试图进行图生视频：观察 prepare_upload、上传域名/STS、申请位置、文件 PUT、是否需要 CommitImageUpload、图像块及附件标识。验证内容确实参考了图，不只验证上传 200。
7. 测试两张明显不同的参考图及提示词引用顺序；验证模型接受哪些引用角色。未知首尾帧能力保持不支持状态，不将普通参考伪装成首帧契约。
8. 单独取得文本、流式文本、识图、生图的真实请求和结果；不把视频模板改个 ability_type 就标为全部能力完成。
9. 确认有效账号 A/B 的隔离和真实可用额度。额度耗尽/网络异常优先用离线夹具覆盖，不能为了测试换号把所有真实额度主动耗光。

### 5.3 观察与反代两种运行环境

浏览器中的用户会话只用于本轮授权研究与后续样本验证。生产 Provider 不能依赖用户桌面 Chrome 常开。需要验证通过管理员导入 Cookie/授权状态，或服务器支持的交互登录，在隔离运行环境重新建立会话。

若直接 HTTP 被拒而正常网页成功：保存差异，优先让该账号真实浏览器上下文完成正常请求；会话/CSRF/动态签名随真实页面生命周期生成。若连真实账号网页也无法正常执行，则标记账号需处理，不通过换指纹、重复注册或猜测签名宣称解决。

### 5.4 Go / No-go 决策

| 结果 | 后续动作 |
| --- | --- |
| 登录导入、2.5、5/10/15/30、图生视频都通过 | 固化 schema 与夹具，进入完整实现 |
| 5/10 通过，15/30 失败或实际仍是 10 秒 | 保留实验记录；R06 未完成；报告阻塞与可交付范围，不静默降级 |
| Cookie 可用于 HTTP但无法在容器复现 | 不宣布生产可用；补服务运行环境验证 |
| 只能正常浏览器上下文成功 | 固定 browser-session transport，并验证服务器可运行与恢复 |
| 余额无法读到精确数字 | 显示“未知”，保留上游原始计量单位与真实用量账本；不得伪造剩余次数 |
| 无可靠任务关联或结果查询 | 暂不进入面向普通用户的稳定视频交付，先补关联协议 |
| 参考许可证不足以直接复制 | 独立实现协议/算法，必要模板自主标定；保留来源说明 |

## 6. 本轮验证范围

语法检查通过并不代表依赖锁定、服务可启动、账号有效或上游响应正确。POC 测试只覆盖账本。合成视频处理只覆盖可运行性。当前没有 LIVE_VERIFIED 项，本轮也未捕获一次真实生成的请求体。以上缺口均已有 T01/T02/T14 任务与验收方法，不以推测填成“已完成”。
